Contents

1. How the deployment works today (relevant to the steps)

Covers both the code repo (stlu/upgrade) and the deployment repo (decidim/deployment, ArgoCD, overlays pitc-decidim-stlu-{dev,int,prod}). Written for the one-step variant. For two steps, run phase C once per step image (§5). The same guide is used on INT and then on PROD. References like planning §5.5 point to planning.html.

  • deployments/base/rails.yaml: strategy: Recreate. The init containers are prepare-assets → wait-for-database → migrate-database (bundle exec rails db:migrate). The rails container starts serving immediately after the migration, which is why the site is closed to the public for the whole migration (step 0-down).
  • deployments/base/delayed-job.yaml: the init container bleib:wait_for_migrations waits for schema migrations only.
  • lib/tasks/jobs.rake hooks db:schedule_jobs onto db:migrate. Every migration therefore schedules all CronJob subclasses that are missing. Existing rows are left alone: changed cron expressions don't get updated, and rows for deleted classes remain.
  • The init container doesn't run data:migrate (only db:migrate). 0.31.8 ships real data migrations (decidim-forms/db/data/20260616144141_rename_answers_to_responses.rb, …update_user_groups_references.rb, …add_short_name_to_organizations.rb, …change_users_in_action_logs_*.rb). Zürich's PROD has them anyway: data_migrations on stzh-prod contains all 10 that apply. The only one missing is 20260208135004 (initiatives), which is expected because Zürich doesn't use decidim-initiatives. So Zürich ran them outside the init container. For decidim.swiss all 11 are due, including initiatives. Either add data:migrate to the init container (step A3) or run it explicitly as a runbook step right after C1.
  • base/environments.yaml already sets STORAGE_PROVIDER=$(ACTIVE_STORAGE_SERVICE) and the DECIDIM_* variables (left over from Zürich #595). The ENV side of the 0.31 config switch is largely done; changes to base also apply to stzh.
  • ArgoCD: INT and PROD are deployed manually via ArgoCD sync; only DEV deploys automatically. Images are pinned by newTag: git-<sha> and copied to the PROD registry with ruby-ops/bin/copy-docker-image.
  • Taking the site down: rails keeps running (tasks, smoke tests). Public access is blocked at the OpenShift level with an IP whitelist for the team, the established procedure. The team keeps working on the real tenant hostnames.

Shell setup (used by all commands below)

ENV=int   # or prod / dev
oc project pitc-decidim-stlu-$ENV
pod() { oc get pods -l app=rails -o name | cut -d/ -f2 | head -n1; }      # re-evaluated on every call, survives redeploys
r()   { oc exec -c rails "$(pod)" -- bundle exec rails "$@"; }            # r decidim:taxonomies:make_plan
rr()  { r runner "$1"; }                                                   # rr 'puts Decidim::Organization.count'
db()  { oc exec -i postgresql-0 -c postgresql -- bash -c "$1"; }          # db 'psql "$POSTGRES_DB" -c "select 1"'
bucket() { oc get secret ocp4-s3-storage -o jsonpath='{.data.bucket}' | base64 -d; }
s3()  { local j; j=$(oc get secret ocp4-s3-storage -o json) || return 1   # aws s3 via docker, credentials from the secret,
        docker run --rm -u "$(id -u):$(id -g)" -e HOME=/tmp -e AWS_DEFAULT_REGION=none -v "$PWD/dumps:/dumps" \
          -e AWS_ACCESS_KEY_ID="$(jq -r '.data["access-key-id"] | @base64d' <<<"$j")" \
          -e AWS_SECRET_ACCESS_KEY="$(jq -r '.data["secret-access-key"] | @base64d' <<<"$j")" \
          amazon/aws-cli --endpoint-url "$(jq -r '.data.endpoint | @base64d' <<<"$j")" s3 "$@"; }   # ./dumps is /dumps inside

2. Phase A: preparation (weeks before)

#Repo / placeStep
A1TenantsAnnounce the freeze of scopes, areas, categories and process/assembly types from date X. Each tenant submits its target taxonomy plan. Also announce the maintenance window, SMS re-verification, user group mails, removal of the "Appearance" page, header snippets without JS, and signature workflows (initiatives).
A2PROD (read-only)Data checks per organization: user groups (decidim_users.type = 'Decidim::UserGroup'), initiative types with online signature, header snippets containing <script, sortitions/collaborative drafts/meeting polls, maps provider HERE, size of the delayed_jobs queue (failed and pending).
A3Deployment repoLeave the migrate-database init container unchanged during the upgrade. base is shared with stzh, and stlu on 0.29 has no data_migrate gem, so data:migrate there would break stlu's deployments. Only after stlu-prod is on 0.31 switch it to bundle exec rails db:migrate && bundle exec rails data:migrate (follow-up). New ENV only if needed (DECIDIM_API_JWT_SECRET, DECIDIM_VERIFICATION_*, DECIDIM_CACHE_EXPIRATION_TIME).
A4Deployment repoPrepare step commits/tags per overlay:
  • upgrade-0.31/stlu-<env>/0-down: OpenShift IP whitelist for the team only (usual procedure)
  • upgrade-0.31/stlu-<env>/1-deploy: images.rails.newTag: git-<sha>, delayed-job: 0, rails-metrics-exporter: 0
  • upgrade-0.31/stlu-<env>/2-up: delayed-job: 1, rails-metrics-exporter: 1, public access restored
A5Code repoFinal commit on upgrade → tag upgrade-0.31/step-1 (plus step-2 for the two-step variant) → manual build stlu-int → copy-docker-image to the PROD registry, keeping the same git-<sha>.
A6Code repoRunbook scripts/upgrade_runbook.rb covers phases B and C in order: <env> status | run | redo <step> | reset. State in tmp/runbook/<env>/state.yml (status, start/end, duration, exit code, command), one log per step next to it. run skips done steps and stops at the first failure; manual steps (ArgoCD syncs, smoke test, go/no-go) ask for confirmation; non-idempotent steps (import_all_plans, revoke:sms, user_groups:remove) only re-run when the step id is typed. RUNBOOK_DRY=1 prints the commands only; SHA=… makes the image check exact. /dumps and /plans are git-ignored (PROD data).
A7DEV (PROD copy)Load the PROD dump into DEV. Run the full phase C there. Write the timings to state.yml. Before loading: SMTP to a catcher, no ASPSMS, a separate S3 bucket.
A8INTRun phases B–D against the exact images, tags and guide. This is the dress rehearsal.
A9Local diskS3 backup by ourselves: mirror the bucket to dumps/s3-<env> with aws s3 sync (docker, credentials from the ocp4-s3-storage secret). Initial sync in phase A, so the sync on deploy day only transfers changes. Restore is the same sync in the other direction. No coordination with other teams needed.
A10IssuesKeep decidim.swiss#228 current: estimate and decisions → DEV rehearsal done → INT ready for acceptance → PROD date → PROD done. Close the loop on #231 and #219.
